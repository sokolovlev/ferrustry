# Архитектура Ferrustry

Статус: **утверждено 2026-11-15**. Реализованы крейты `ferrustry-content`, `ferrustry-sim`,
`ferrustry-format`, `ferrustry-headless`; остальные появятся на своих этапах.

Ferrustry — оригинальная игра жанра «автоматизация производства + защита базы» на Rust.
Ключевое требование: игровая симуляция полностью отделена от графики и работает headless —
одно ядро для клиента, выделенного сервера, тестов и бенчмарков.

## 1. Принципы

1. **Headless-first.** Крейт симуляции не зависит от wgpu, winit, аудио и сети.
2. **Фиксированный шаг.** Симуляция тикает с постоянной частотой; рендер интерполирует.
3. **Детерминизм.** Один и тот же бинарник + одинаковые входные команды + одинаковый seed ⇒
   побитово одинаковое состояние. Проверяется хешем состояния в тестах.
4. **Данные отдельно от кода.** Контент (ресурсы, блоки, юниты, рецепты) описывается данными
   и загружается в реестр; системы работают с числовыми ID.
5. **Data-oriented.** Плотные массивы (SoA) по типам объектов, инкрементальные структуры
   (сегменты конвейеров, сети энергии), минимум аллокаций в тике.
6. **Измерять, потом оптимизировать.** Параллелизм — только после профилирования и только
   с детерминированным порядком слияния результатов.

## 2. Структура workspace

Крейты создаются по мере появления реального кода — без пустых заготовок.

```text
ferrustry/
├── Cargo.toml                 # workspace, общие lints и профили
├── crates/
│   ├── ferrustry-sim/         # Этап 1: мир, контент-реестр, системы, тик, хеш состояния
│   ├── ferrustry-content/     # Этап 1: схемы контента (serde) + базовый набор данных
│   ├── ferrustry-format/      # Этап 1: формат карт/сохранений/схем, версионирование
│   ├── ferrustry-headless/    # Этап 1: бинарник — прогон сценариев, бенчмарки, replay
│   ├── ferrustry-render/      # Этап 2: wgpu-рендерер (спрайты, тайлы, камера)
│   ├── ferrustry-client/      # Этап 2: winit-приложение, ввод, UI, связывает sim+render
│   ├── ferrustry-audio/       # Этап 4+: звук (кандидат — kira)
│   ├── ferrustry-net/         # Этап 6: протокол, сериализация пакетов, транспорт
│   └── ferrustry-server/      # Этап 6: выделенный сервер (sim + net, без графики)
├── assets/                    # оригинальные ассеты Ferrustry (своя лицензия, см. licensing.md)
├── benches/ / tests/          # сценарии бенчмарков и интеграционные тесты
└── docs/
```

Граф зависимостей (стрелка = «зависит от»):

```text
content ← sim ← format
            ↑      ↑
   headless ┘      │
   render ← client ┤ (client → sim, format, render, audio, net)
   net ← server ───┘ (server → sim, format, net)
```

`ferrustry-core` как отдельный крейт **не заводится**, пока у sim и net не появится реально общий
код (ID, математика фиксированной точки). Если появится — выделим.

## 3. Игровой цикл

- **Частота симуляции: 30 тиков/с** (предложение; см. decisions.md, D-03). Бюджет тика — 33,3 мс,
  целевой — существенно меньше, чтобы сервер вытягивал большие карты и несколько игр на ядро.
- Клиент: `accumulator`-цикл — N тиков симуляции за кадр (с ограничением «спирали смерти»),
  рендер интерполирует позиции юнитов/снарядов между двумя последними состояниями.
- Порядок систем в тике фиксирован и задокументирован:

```text
1. применить входные команды игроков (строительство, приказы)   — упорядочены по (tick, player_id, seq)
2. строительство/снос → инкрементальные перестроения (сегменты, сети, flow fields)
3. энергосети: баланс производства/потребления → коэффициент удовлетворения
4. добыча и производство (используют коэффициент энергии из шага 3)
5. логистика: сегменты конвейеров, сортировщики, хранилища
6. жидкости
7. юниты: ИИ → движение (flow field + локальное избегание) → столкновения
8. турели: выбор цели (spatial grid) → выстрелы
9. снаряды: движение, попадания, урон
10. смерть/разрушение, очистка, события для клиента
11. волны противников
12. (debug/test) хеш состояния
```

## 4. Мир и хранение данных

### Сетка
- Мир делится на **чанки 32×32 тайла**. Тайл = пол (terrain) + руда (overlay) + ссылка на постройку.
- Пол/руда — плотные массивы `u16` внутри чанка (кэш-дружественно, легко сериализуется и рендерится).
- Многотайловые постройки: тайл хранит `BuildingId`, сама постройка хранит origin и размер.

### Постройки
- Не «объект на тайл», а **таблицы по виду поведения** (drill, crafter, conveyor-segment,
  storage, turret, power-node…): плотные SoA-массивы + generational `BuildingId → (kind, index)`.
- Удаление — swap-remove с обновлением индекса. Это даёт линейный проход по однотипным
  постройкам без виртуальных вызовов.

### Динамические сущности (юниты, снаряды)
- Кандидаты: `hecs` или собственные SoA-пулы. Предложение: **собственные пулы** для снарядов
  (их больше всего, жизнь короткая) и `hecs` для юнитов на этапе 4 с возможной заменой
  после профилирования (decisions.md, D-05).
- Пространственный индекс: uniform grid (ячейка = чанк или 8×8 тайлов), перестраивается за тик
  за O(n) — для поиска целей, столкновений и урона по площади.

## 5. Ключевые подсистемы

### Логистика (конвейеры)
Самое горячее место жанра. Модель:
- Цепочка соединённых конвейеров одного направления объединяется в **сегмент** (transport line).
- Сегмент хранит предметы как массив `(item_id, gap_to_next)`; движение = уменьшение одного
  «головного» зазора, а не обход всех предметов. Стоимость тика ~O(число сегментов), а не O(предметов).
- Сегменты перестраиваются **инкрементально** только при постройке/сносе соседних тайлов.
- Узлы (разветвители, сортировщики, мосты, входы машин) — отдельные таблицы с буферами,
  взаимодействуют с концами сегментов.

### Энергия
- Сеть = связная компонента графа (узлы + постройки).
- Добавление — union-find (почти O(1)); удаление — перестроение только затронутой компоненты (BFS).
- Каждая сеть кэширует сумму производства/потребления/ёмкости батарей; тик баланса — O(число сетей).
- Недостаток энергии → коэффициент удовлетворения `0..1`, который потребители применяют к скорости.

### Жидкости
- Тот же граф-подход, что у энергии, но с объёмом и пропускной способностью по сегментам
  (компартментная модель). Точная модель — геймдизайнерское решение (decisions.md, D-09).

### Юниты и поиск пути
- **Flow fields** по классам передвижения (наземный / тяжёлый / летающий) к целям (ядро игрока,
  точка сбора). Пересчёт инкрементально по чанкам при изменении проходимости.
- A* — только для единичных приказов игрока; иерархический вариант (по чанкам) при необходимости.
- Локальное избегание: разделение (separation) по spatial grid; физика — круги, без полноценного
  физического движка.

### Бой
- Турели: выбор цели через spatial grid с ограничением частоты перевыбора.
- Снаряды: пул SoA, проверка попаданий по grid; урон, броня, разрушение построек → события
  для перестроения логистики/энергии.

## 6. Числа и детерминизм

- Логика сетки, предметов, энергии, жидкостей — **целые числа** (энергия в целых «микроединицах»).
- Позиции юнитов/снарядов — `f32` без FMA-зависимых и трансцендентных функций из std в
  логике симуляции (используем `libm`-эквиваленты), чтобы результат не зависел от платформы.
  Альтернатива — фиксированная точка (decisions.md, D-04).
- ГПСЧ — собственный (например, PCG/xoshiro) с явным seed в состоянии; никакого `thread_rng` в sim.
- Порядок итерации — только по стабильным индексам/ID, никаких `HashMap` с рандомным хешером в
  логике, влияющей на состояние.

## 7. Контент и моддинг

- Контент описывается в **RON** (или TOML) и загружается в `ContentRegistry` с проверкой ссылок
  (рецепт ссылается на существующий ресурс и т. п.). Ошибки контента — понятные сообщения, не паника.
- Поведение блоков — фиксированный набор «видов поведения», параметризуемых данными.
  Это первая ступень моддинга (data-only моды).
- Скриптовые моды (WASM через wasmtime или Lua через mlua) — после этапа 6, отдельное решение (D-10).

## 8. Рендеринг (этап 2)

- `wgpu` + `winit` (стабильная ветка winit 0.30; 0.31 сейчас в beta).
- Атлас текстур, **instanced sprite batching** (один draw call на слой/атлас).
- Статические слои (пол, руда) — меши по чанкам, кэшируются и перестраиваются при изменении.
- Видимые чанки — frustum culling по камере.
- Рендер читает **снимок** состояния (или интерполяцию двух снимков), не изменяет симуляцию.
- UI: см. decisions.md, D-07.

## 9. Сеть (этап 6)

- **Авторитарный сервер**: сервер — единственный источник истины.
- Клиент шлёт команды (строить, приказ юнитам, взаимодействие), сервер шлёт:
  полный снимок при подключении (через формат сохранений) + дельты/события по тикам.
- Предсказание на клиенте — для собственного юнита/курсора строительства.
- Транспорт: UDP с собственным reliable/unreliable-каналом или готовое решение (renet / QUIC через quinn).
  Решение после прототипа (D-08). `tokio` используется только в net/server, sim остаётся синхронным.
- Протокол версионируется; несовпадение версий — понятная ошибка при подключении.

## 10. Форматы

См. compatibility.md. Кратко: один контейнерный бинарный формат (заголовок + версия + секции,
сжатие zstd) для карт, сохранений и схем; пакеты сети — `postcard` поверх serde.

## 11. Обработка ошибок и качество

- Библиотечные крейты: `thiserror`-типы ошибок; бинарники: `anyhow`/`eyre` на верхнем уровне.
- Нет `unwrap/expect` в runtime-путях без комментария-обоснования; `unsafe` запрещён
  `#![forbid(unsafe_code)]` во всех крейтах, кроме явно согласованных мест в рендере.
- CI: `fmt --check`, `clippy -D warnings`, `test`, `build --release` на Linux/Windows/macOS.

## 12. Реализация этапа 1 (что сделано фактически)

| Модуль | Файл | Суть |
|---|---|---|
| Контент | `ferrustry-content/src/lib.rs`, `data/base.ron` | RON → валидация ссылок/значений → `ContentRegistry` с `u16`-ID |
| Сетка | `ferrustry-sim/src/grid.rs` | Чанки 32×32: пол, руда, ссылка на постройку |
| Постройки | `ferrustry-sim/src/buildings.rs` | Generational-арена + плотные таблицы по виду поведения (swap-remove) |
| Конвейеры | `ferrustry-sim/src/segment.rs`, `world.rs` | Сегменты ≤ 32 тайлов с зазорами, кэш сжатого префикса, повороты, циклы, локальная перестройка с сохранением предметов; упакованная раскладка `item<<16 \| gap`; усыпление (битсет активных + списки ожидающих); кэш связей по эпохе топологии |
| Энергия | `ferrustry-sim/src/power.rs` | Union-find по касанию и радиусу узлов, коэффициент удовлетворения в тысячных |
| Производство | `world.rs` | Буры (доля руды под буром), рецепты, round-robin выгрузка по периметру |
| Детерминизм | `hash.rs`, `rng.rs` | FNV-1a по сериализованному состоянию, xoshiro256** в состоянии мира |
| Формат | `ferrustry-format` | Контейнер v1.0, zstd, CRC32, таблица имён, проверка целостности |
| Headless | `ferrustry-headless` | `run`, `resume`, `save-check`, `bench` с JSON-отчётом и счётчиком аллокаций |

Отклонения от плана, о которых нужно знать:
- Порядок систем в тике сейчас: энергия → буры → производства → конвейеры (юнитов, жидкостей,
  боя ещё нет). Команды применяются до систем в переданном порядке.
- Энергосеть перестраивается целиком при любом изменении энергопостроек (локальная перестройка — S3-02).
- Строительство мгновенное и бесплатное (режим песочницы); стоимость и время стройки — этап 3.
- Предмет, вышедший из сегмента в сегмент с большим индексом, может сдвинуться ещё раз в том же
  тике. Поведение детерминировано; если оно станет заметным, введём двухфазное обновление.

### Планировщик логистики (с 2026-11-15)

- Обрабатываются только **бодрствующие** сегменты, строго по возрастанию индекса (битсет).
- Сегмент засыпает, если ничего не изменилось и: он пуст; или предметы полностью сжаты, а выход
  упирается в пустоту / постройку, не принимающую предметы / спящий сегмент (тогда он
  записывается в список ожидающих этого сегмента).
- Будят: успешная вставка; движение или выдача предметов у сегмента, которого ждут; стройка рядом.
- Получатель на выходе сегмента и список получателей выгрузки постройки кэшируются и
  сбрасываются ростом **эпохи топологии** (любая стройка/снос).
- Режим `World::set_sleep_enabled(false)` — эталон для дифференциальных тестов.

|---|---|---|

| Батареи | `power.rs` | Избыток сети заряжает, нехватка разряжает; удовлетворение спроса учитывает разряд; распределение по батареям детерминировано |
| Настройка | `Command::Configure` | Фильтр сортировщика; проходит через replay как любая команда |
| Инспектор | `World::inspect` → `Detail` | Структурированное состояние постройки для UI |

Найдено и исправлено по ходу: снос не увеличивал эпоху топологии, и кэши связей
(сегменты, выгрузка) оставались устаревшими до следующей постановки — предметы могли уходить
по неверной связи. Регрессионный тест `removal_invalidates_cached_links` падает без исправления.

## 15. Жидкости и тепло (2026-11-17, решения D-02, D-09)

| Что | Суть |
|---|---|
| Сети | `thermal.rs`: постройки, касающиеся сторонами, образуют жидкостную (объём, один вид жидкости) или тепловую (запас тепла, теплоёмкость) сеть; union-find при изменении |
| Перестройка | Содержимое старой сети делится между уцелевшими участниками пропорционально ёмкости, остаток — первому; доля снесённых теряется и учитывается (`FluidStats.destroyed`) |
| Тепло | Производство с `heat > 0` выделяет тепло пропорционально скорости (дробная часть копится без потерь); выше 70% заполнения сети скорость падает линейно до 0 при 100% |
| Отвод тепла | Пассивное охлаждение производства, радиатор, градирня (вода → тепло), тепловая машина (тепло → энергия на следующий тик, КПД 50%) |
| Вода | Конденсатор делает воду из энергии; трубы соединяют конденсаторы и градирни |
| Порядок тика | перестройка сетей → энергия → конденсаторы → буры → производства (тепло) → тепло → роутеры → мосты → ленты |

Проверено тестами с точными ожиданиями: перегретая кузница выходит на равновесие ровно 950‰
и 1/6 скорости (9 циклов против 50 у охлаждаемой за 3000 тиков); вода учитывается до единицы
при перестройке сети.

## 16. Бой (этап 4, 2026-11-17)

| Что | Суть |
|---|---|
| Числа | Позиции в 1/256 тайла (`combat::SUB`), расстояния — `i64::isqrt`; никаких `f32` в симуляции → бой детерминирован между x86 и ARM |
| Юниты, снаряды | SoA-пулы (`Units`, `Projectiles`), удаление swap-remove с конца |
| Поле путей | Дейкстра от всех тайлов ядер; вход в пустой тайл = 1, в тайл постройки = 1 + прочность/8 (стена ≈ 51 тайл обхода); пересчёт только при смене эпохи топологии и наличии юнитов |
| Поведение врага | Шаг к соседу с меньшей стоимостью; если там постройка — удар с перезарядкой; у ядра — удар по ядру |
| Сетка | Ячейки 2×2 тайла, списки «голова + следующий» без аллокаций; служебный буфер `Scratch` не сохраняется и не участвует в сравнении миров |
| Турель | Ближайшая цель в радиусе через сетку, упреждение по смещению цели за тик, снаряды со временем полёта; боеприпасы — предметы с ленты |
| Разрушение | `World::destroy_at`: как снос, но без возврата стоимости; последнее ядро → `Outcome::Lost` |
| Волны | По таймеру из точек появления карты; состав растёт с номером (`World::wave_composition`) |
| Порядок тика | … ленты → волны → юниты → сетка → расталкивание → сетка → турели → снаряды → удаление убитых |

Баланс v0 (проверен тестом): одна турель надёжно останавливает трёх одновременных краулеров.

## 17. Карты и схемы (этап 5, 2026-11-17)

| Что | Где | Суть |
|---|---|---|
| Генератор | `ferrustry-sim/src/mapgen.rs` | Шум значений на целых числах (одинаковая карта на любой платформе); пепел, шлаковые озёра вдали от старта; руды: сначала случайные, затем гарантированные у старта (их нельзя перекрыть); площадка у ядра; точки появления на краях с гарантированным путём (иначе прорубается коридор) |
| Сложность | `Difficulty` | Темп волн: лёгкая 8/3 мин, обычная 5/2, сложная 3/1,5 |
| Схемы | `ferrustry-sim/src/schematic.rs` | Копия построек в рамке (поворот, фильтр сортировщика), поворот на 90° с учётом размеров, вставка как обычные команды (`Place` + `Configure`) — экономика, replay и сеть работают автоматически |
| Файл схемы | `ferrustry-format/src/schematic.rs` | Постройки по именам контента; неизвестное имя — ошибка, а не догадка |

## 18. Контент v0.4 (2026-11-17)

| Что | Механика | Почему так |
|---|---|---|
| Топливный генератор (`Generator` с `fuel`) | Буфер топлива, предмет горит `burn_ticks` тиков | Тот же вид постройки, что ветряк: без новой таблицы. Горит независимо от спроса (v0) |
| Постоянная выработка | Сумма ветряков сети — при перестройке сети | Каждый тик обходятся только топливные генераторы (−6,4% инструкций на B3) |
| Склад (`Depot`) | Принимает с трёх сторон, выдаёт с передней по 1 предмету за тик; если предмет не берут — пробует следующий вид | Склад со смесью не застревает перед производством, которому нужен другой предмет |
| Дуговая турель (`ArcTurret`) | Перезарядка ускоряется питанием сети (500‰ — вдвое дольше), мгновенный урон, игнорирует броню | Делит таблицу турелей с пушкой; спрос на энергию — только пока заряжается |
| Броня врагов | Урон снаряда минус броня, но не меньше трети | Пушка против панцирника слаба, но не бесполезна |
| Дальнобойные враги | Ищут ближайшую постройку в радиусе (квадрат тайлов, по строкам — детерминированно), стоят и стреляют до конца перезарядки | Снаряды врагов — в том же SoA, флаг `hostile`; попадают в любую постройку на своём тайле |

Перезарядка турелей теперь идёт каждый тик, даже без врагов (раньше замирала вместе с боевым шагом).
