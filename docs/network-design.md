# Сетевая игра: проект (этап 6)

Статус: **проект на согласовании** (2026-11-20). Решения D-18…D-22 — в [decisions.md](decisions.md).
Всё, что ниже названо числом, измерено (`examples/net_estimates.rs`, облачная VM; на ПК владельца
быстрее), а не обещано.

## 1. Главный вопрос: что передавать по сети

Есть два способа держать мир у игроков одинаковым.

| | **Рассылка состояния** (снимок + изменения) | **Рассылка команд** (детерминированная симуляция у всех) |
|---|---|---|
| Что идёт по сети | Изменения мира каждый тик | Только команды игроков, упорядоченные сервером |
| Кто считает мир | Сервер; клиенты показывают | Сервер и каждый клиент — одну и ту же симуляцию |
| Трафик растёт с | Размером базы | Числом действий игроков |
| Требует | Отслеживание изменений во всех системах | Детерминизм на всех платформах |
| Плюсы | Клиенту не нужен мощный процессор; можно скрывать карту (туман войны в PvP) | Почти нулевой трафик; база любого размера; клиент — это та же одиночная игра |
| Минусы | Трафик и цена поиска изменений растут с базой | Рассинхронизация при ошибке детерминизма; клиент видит весь мир; вход в партию требует снимка |

Детерминизм у нас уже есть и проверяется: целочисленная симуляция, state hash, в CI повтор, записанный
на Linux x86_64, воспроизводится бит в бит на Windows x86_64 и macOS ARM64.

## 2. Замеры

Изменения за тик — нижняя оценка: побайтная разница сериализованного мира до и после тика, сжатая zstd.
Настоящий протокол дельт передавал бы не меньше и ещё тратил бы время на поиск изменений.

| Сценарий | Состояние | Снимок (сжатое сохранение) | Изменения за тик | Трафик состояния на клиента | Сериализация мира | `state_hash` |
|---|---|---|---|---|---|---|
| B3-10k (14 тыс. построек) | 682 КБ | 164 КБ, запись 4 мс, чтение 6 мс | 3,4 КБ (≥ 1,7 КБ сжато) | **≥ 49 КБ/с** | 1,4 мс | 2,4 мс |
| B3-100k (125 тыс. построек) | 7,1 МБ | 1,6 МБ, запись 47 мс, чтение 62 мс | 34 КБ (≥ 15 КБ сжато) | **≥ 447 КБ/с** (3,6 Мбит/с) | 17 мс | 28 мс |
| B5 (1000 врагов, 300 турелей) | 127 КБ | 10 КБ | 3,7 КБ (≥ 3 КБ сжато) | ≥ 87 КБ/с | 0,2 мс | 0,35 мс |

Команда стройки (тик, игрок, команда) — **10 байт**. Восемь игроков по 5 команд в секунду — 0,4 КБ/с на всех.

Выводы:

- При рассылке состояния мегабаза требует ≥ 3,6 Мбит/с на **каждого** клиента (8 игроков — ≥ 29 Мбит/с
  исходящих у сервера), а поиск изменений через сериализацию стоит 17 мс — половину бюджета тика при
  тике самой симуляции 0,3 мс. Чтобы было дешевле, пришлось бы встроить отслеживание изменений во все
  системы — крупная переделка с риском ошибок в каждой.
- Рассылка команд не зависит от размера базы и укладывается в доли килобайта в секунду.
- Снимок для входа в партию приемлем даже для мегабазы (1,6 МБ, чтение 62 мс).
- `state_hash` слишком дорог для частой сверки (28 мс на мегабазе): нужна дешёвая контрольная сумма
  (задача S6-04).

## 3. Предлагаемая модель (D-18 — D-22)

**Авторитетный сервер + рассылка команд** (D-18):

1. Клиент отправляет команду серверу и сразу показывает «призрак» постройки (как сейчас в одиночной игре).
2. Сервер назначает команде тик исполнения — ближайший ещё не рассчитанный — и рассылает всем **кадр**:
   номер тика и команды этого тика (кадр уходит каждый тик, даже пустой, — это и есть «можно считать дальше»).
3. Сервер и клиенты считают один и тот же тик с одними и теми же командами. Клиент считает тик, только
   когда получил его кадр; небольшой буфер сглаживает неравномерную доставку (D-19).
4. Раз в несколько секунд сервер рассылает контрольную сумму своего состояния; клиент сравнивает со своей.
   При расхождении клиент получает свежий снимок и продолжает с него (D-20); отчёт о расхождении с номером
   тика сохраняется для отладки (как в replay).
5. Вход в идущую партию: сервер делает снимок (копия мира — миллисекунды, сериализация — в отдельном
   потоке, чтобы не задерживать тик), клиент загружает его и догоняет по кадрам, считая тики быстрее
   реального времени (тик мегабазы — 0,3 мс, т. е. ~3000 тиков в секунду) (D-21).

Задержка действия игрока = время до сервера и обратно + буфер. Для стройки в игре про заводы это
приемлемо, а призрак убирает ощущение задержки. Отказы команд (нет ресурсов, место занято) определяются
симуляцией одинаково у всех.

Сервер — тот же `ferrustry-sim` без графики; транспорт — по D-08 (renet). Для тестов — транспорт в памяти:
сервер и несколько клиентов в одном процессе, проверка «все state hash совпадают» на тысячах тиков.

## 4. Что не входит в первую версию

- PvP с туманом войны: при рассылке команд у клиента весь мир. Первая версия — кооператив (D-22).
- Защита от читов на клиенте: сервер проверяет право игрока на команду, но клиент видит всё.
- Переподключение с сохранением места в очереди: при разрыве клиент входит заново через снимок.
- Многопоточность симуляции по регионам (D-17, вариант Б): модель команд от неё не зависит — регионы
  можно добавить позже без изменения протокола, если детерминизм сохранится.

## 5. Риски

| Риск | Что делаем |
|---|---|
| Ошибка детерминизма → рассинхронизация | Уже: целые числа, запрет недетерминированных API, повтор между ОС в CI. Добавим: тест «сервер + 3 клиента» на тысячах тиков, контрольная сумма с номером тика, автоматическое восстановление через снимок |
| Медленный клиент отстаёт | Клиент считает несколько тиков за кадр (как сейчас при ускорении); если отстаёт больше N секунд — предупреждение и вход заново |
| Пиковая задержка сервера при снимке | Копия мира в основном потоке, сериализация и сжатие — в фоне |
| Дорогая контрольная сумма | Задача S6-04: быстрый хеш (не по сериализации) или сверка по частям мира по очереди |
